01개발 구조

Frontend / Backend

프론트엔드 / 백엔드

프론트엔드는 사용자가 보는 화면, 백엔드는 뒤에서 데이터를 처리·저장하는 서버

FRONTEND브라우저 화면
리프팅 상담
BACKEND서버받아서 검사·처리
DATABASEDB창고(저장)
화면 속 예약하기 버튼을 눌러봐
// FRONTEND (브라우저에서 실행) — 화면 + 요청 보내기
button.onclick = () => fetch('/api/reservations', { method:'POST', body });

// BACKEND (서버에서 실행) — 받아서 검사하고 DB에 저장
app.post('/api/reservations', async (req, res) => {
  await db.insert(req.body);        // DATABASE에 저장
  res.status(201).json({ ok:true });  // 결과 돌려주기
});
외우기식당으로 치면 프론트 = 홀(손님이 보는 곳), 백엔드 = 주방, DB = 창고.
실전 프롬프트
이 기능을 프론트엔드(화면)와 백엔드(서버) 작업으로 나눠서 정리해주고, 백엔드 없이 정적 사이트(GitHub Pages)로 가능한지 먼저 판단해줘.
02개발 구조

Framework

프레임워크

자주 필요한 구조(화면 조각, 페이지 이동, 빌드 등)를 미리 갖춰 둔 개발 뼈대(React, Next.js 등)

    # Next.js 새 프로젝트 만들기
npx create-next-app@latest my-app

# 폴더 = 주소 (App Router)
app/page.tsx         →  /
app/event/page.tsx   →  /event
    React는 엄밀히 “화면 라이브러리”, Next.js는 React 위에 라우팅·서버·SEO까지 얹은 “프레임워크”야. 이 스터디 사이트처럼 단순한 페이지는 HTML만으로도 충분해.
    외우기집 짓는 골조(뼈대). 기둥·배관(라우팅·화면 갱신)을 미리 깔아줘서 나는 방(기능)만 꾸미면 됨.
    실전 프롬프트
    이 프로젝트는 Next.js(App Router) 기준으로 만들어줘. 시작 전에 페이지별 폴더 구조부터 보여주고, 정적 배포가 가능한지도 알려줘.
    03개발 구조
    Tailwind CSS
    테일윈드 CSS
    미리 만들어진 짧은 클래스 이름(bg-pink-500, p-4 등)을 조합해 스타일을 입히는 CSS 도구
    클래스를 하나씩 켜봐. 버튼 모양이 바뀌고, 아래 코드의 class="..."가 그대로 따라 바뀌어.
    <!-- CSS 파일 없이 class로 바로 스타일 -->
<button class="bg-pink-500 text-white px-6 py-3 rounded-full shadow-lg font-bold hover:scale-105">
  상담 예약
</button>

<!-- md: = 768px 이상에서만 적용 (반응형) -->
<div class="grid grid-cols-1 md:grid-cols-3 gap-4">...</div>
    외우기CSS 파일 대신 class 이름 = 스타일. bg(배경)·text(글자)·p(안쪽 여백)·rounded(둥글기) 단어만 알면 읽혀.
    실전 프롬프트
    스타일은 Tailwind CSS 클래스로만 작성하고, 브랜드 핑크는 pink-500 계열로 통일해줘. 반응형은 md: / lg: 접두사로 처리해줘.
    04개발 구조
    Component · Props · State
    컴포넌트 · 프롭스 · 스테이트
    컴포넌트는 재사용하는 화면 조각, props는 밖에서 넣어주는 값, state는 컴포넌트가 스스로 기억하며 바뀌는 값
    <TreatCard name="…" time="…" /> ← 틀 1개
    선택한 카드 속 값
    카드를 눌러 선택 → ♡를 눌러 state 바꾸기 → 아래 칸에서 name(props)을 바꿔봐. 같은 틀(컴포넌트)인데 재료(props)만 달라.
    function TreatCard({ name, time }) {           // props: 밖에서 받는 값
  const [liked, setLiked] = useState(false);   // state: 스스로 기억하는 값
  return (
    <div className="card">
      <b>{name}</b> <span>{time}</span>
      <button onClick={() => setLiked(!liked)}>{liked ? '♥' : '♡'}</button>
    </div>
  );
}
<TreatCard name="리프팅" time="30분" />       // 같은 틀, 다른 재료
<TreatCard name="스킨부스터" time="20분" />
    외우기Component = 붕어빵 틀, Props = 틀에 넣는 재료(밖에서 줌), State = 붕어빵이 스스로 가진 상태(찜 여부).
    실전 프롬프트
    시술 카드를 컴포넌트로 분리하고 name·time·tag를 props로 받게 해줘. 찜(♡) 여부는 카드 안의 state로 관리해줘.
    05개발 구조
    API
    API (에이피아이)
    프로그램끼리 정해진 주소·형식으로 데이터를 주고받는 창구(요청 → 응답)
    FRONT화면
    API주문 창구
    SERVER주방
    요청 (Request)
    버튼을 눌러 요청을 보내봐
    응답 (Response)
    …
    // 요청(Request): 이 주소로, 이 방식(GET/POST)으로
const res = await fetch('/api/events');        // GET = 달라고 하기

// 응답(Response): 상태 코드 + 데이터
res.status;   // 200 성공 · 201 만들어짐 · 404 없음 · 500 서버 오류
const data = await res.json();
    외우기식당 주문 창구. 메뉴판(주소·형식)대로 주문(요청)하면 음식(응답)이 나옴. 200 = 성공, 404 = 그런 메뉴 없음.
    실전 프롬프트
    예약 폼 제출 시 POST /api/reservations 로 보내고, 성공(201)·실패(4xx/5xx) 각각 화면 메시지를 처리해줘. 요청/응답 예시도 같이 적어줘.
    06개발 구조
    JSON
    JSON (제이슨)
    데이터를 "키": 값 형태로 적는, 프로그램끼리 주고받는 표준 텍스트 형식
    "키": "문자" · 숫자 · true/false · [목록]
    왼쪽 칸을 바꿔봐. 오른쪽 JSON이 실시간으로 바뀌어 — 폼 데이터가 서버로 갈 때 이런 모양이야.
    {
  "name": "홍길동",          // 문자는 "큰따옴표"
  "treatment": "리프팅",
  "visits": 1,               // 숫자는 그대로
  "marketing": false,        // 참/거짓
  "tags": ["첫방문", "상담"]   // 목록은 [ ]
}
/* 실제 JSON 파일엔 주석(//)을 못 씀 — 여긴 설명용 */
    외우기데이터의 택배 송장 양식. { } 안에 "키": 값 짝꿍을 쉼표로 나열. 키는 꼭 큰따옴표, 마지막엔 쉼표 X.
    실전 프롬프트
    시술 목록 데이터를 treatments.json 파일로 분리하고, 화면은 그 JSON을 읽어서 카드로 그려줘. 나중에 시술 추가는 JSON만 수정하면 되게 해줘.
    07Git
    Repository
    레포지토리(저장소)
    프로젝트 파일과 모든 변경 이력을 함께 보관하는 저장소(GitHub의 repo)
    byeonghoyoo / my-clinic-sitePublic
    변경 이력 (커밋) — 눌러보면 그때 바뀐 줄이 보여
    # 내 컴퓨터 폴더를 저장소로 만들기
git init

# GitHub 저장소를 내 컴퓨터로 복사해오기
git clone https://github.com/byeonghoyoo/my-clinic-site

# 기록(커밋) 목록 보기
git log --oneline
    외우기프로젝트 폴더 + 타임머신. 파일과 “언제 뭘 바꿨는지” 기록을 통째로 보관하는 창고.
    실전 프롬프트
    이 폴더를 GitHub 저장소로 만들고 README에 프로젝트 설명·실행 방법·배포 주소를 3줄로 적어줘. 올리면 안 되는 파일은 .gitignore에 넣어줘.
    08Git
    Commit / Push
    커밋 / 푸시
    commit은 변경 내용을 내 컴퓨터 기록에 저장하는 것, push는 그 기록을 GitHub에 올리는 것
    index.html변경 없음
    내 컴퓨터 (Local)
    GitHub (Remote)
    git add .                          # 바뀐 파일을 담기
git commit -m "히어로 문구 수정"     # ① 내 컴퓨터에 세이브
git push origin main               # ② GitHub에 업로드
git status                         # 지금 뭐가 바뀌었는지 확인
    외우기commit = 게임 세이브(내 컴퓨터), push = 클라우드 업로드(GitHub). 세이브만 하고 업로드 안 하면 남들은 못 봐.
    실전 프롬프트
    변경사항을 기능 단위로 나눠 커밋하고, 커밋 메시지는 한국어로 ‘무엇을 왜 바꿨는지’ 한 줄로 써줘. 다 되면 main에 push해줘.
    09Git
    Branch
    브랜치
    원본(main)을 건드리지 않고 갈라져 나와 따로 작업하는 작업 갈래
    git switch -c feature/hero-copy    # 새 브랜치 만들고 이동
# ...수정하고 커밋...
git switch main                    # 원본으로 돌아가기
git merge feature/hero-copy        # 작업한 갈래 합치기
    외우기평행세계 복사본에서 따로 작업 → 괜찮으면 merge로 합치기. 그동안 원본(main)은 안전.
    실전 프롬프트
    main은 건드리지 말고 feature/hero-copy 브랜치를 만들어서 작업해줘. 끝나면 어떤 파일을 바꿨는지 요약해줘.
    10Git
    Pull Request
    풀 리퀘스트(PR)
    내 브랜치의 변경을 원본(main)에 합쳐달라고 요청하고 검토받는 절차(PR)
    ● Open히어로 문구 수정 #12
    feature/hero-copy → main
    - <h1>최고의 피부 관리</h1>
    + <h1>피부 고민, 상담부터 가볍게</h1>
    # 브랜치를 올린 뒤 PR 만들기 (GitHub CLI)
git push -u origin feature/hero-copy
gh pr create --title "히어로 문구 수정" --body "변경 전/후, 확인 방법"

# 승인 후 합치기
gh pr merge 12 --squash
    외우기“제 작업 합쳐도 될까요?” 결재 요청서. 변경 전/후(diff) 보여주기 → 리뷰 → 승인 → merge.
    실전 프롬프트
    작업이 끝나면 PR을 만들어주고, 설명에 변경 전/후 차이·확인 방법·스크린샷 위치를 적어줘.
